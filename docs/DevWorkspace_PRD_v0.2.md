# DevWorkspace 产品需求文档（PRD）

> **产品定位：** 面向个人开发者与小型技术团队的 Local-first AI 开发工作台  
> **产品形态：** 桌面端开发工作台（非通用 IDE 替代品）  
> **文档版本：** v0.2  
> **状态：** 方向确认后的产品定义稿  
> **核心组合：** Monaco Editor + Git 工作流 + 自动 Snapshot + 内置 AI Agent  
> **产品原则：** Local-first / Git-native / Agent-aware / 可恢复 / 可渐进扩展

---

## 0. 一句话定义

一个把**代码编辑、Git 版本管理、自动历史快照和 AI Agent**整合在一起的本地优先开发工作台。开发者可以在同一个工作区内编辑代码、管理 Git、让 Agent 执行任务，并且每一次关键修改都有自动快照作为安全网。

它不是要重新实现一个完整的 VS Code，也不是 Git 的替代品。它要解决的是：**开发者在 AI 参与编码后，如何在一个轻量工作台里完成“编辑—执行—审查—版本管理—回退”的闭环。**

## 1. 产品背景与机会

开发者目前通常在编辑器、终端、Git 客户端和 AI Coding Agent 之间切换。工具分散会带来几个问题：

1. AI Agent 一次任务可能修改多个文件，开发者难以快速判断修改范围和质量。
2. Git 主要记录开发者主动提交的版本，两个 Commit 之间的中间状态缺少可靠、可浏览的历史。
3. Agent 执行前后的状态、普通手动修改和 Git Commit 分散在不同位置，难以形成连续时间线。
4. 出错后，开发者需要手动找 Diff、撤销文件、切换分支或重置工作区，恢复成本较高。

产品以本地工作区为中心，将 Git 和 Snapshot 两套历史机制整合展示，并让 Agent 在受控的工作区里执行任务。

## 2. 产品定位与边界

### 2.1 产品定位

**AI-native Development Workspace：面向 AI 辅助开发流程的轻量开发工作台。**

主要服务于个人开发者、独立开发者和小型技术团队，尤其是频繁使用 Claude Code、Codex 等 Agent 的开发者。

### 2.2 核心价值

- **统一工作区：** 文件、编辑器、Git、Snapshot、Agent 在一个桌面应用中协同。
- **Git 原生：** 保留标准 Git 仓库和工作流，不发明新的版本控制协议。
- **自动保护：** 不依赖 Commit，自动记录工作区状态；Agent 执行前后自动建立恢复点。
- **可审查：** Agent 的任务、文件变更、Diff 和执行结果可追踪。
- **本地优先：** 源码、Git 仓库、快照和默认 Agent 会话数据保存在本机；云端能力后续可选。

### 2.3 产品边界：做什么

| 范围 | 定义 |
|---|---|
| 桌面工作台 | 项目打开、文件树、标签页、编辑器、集成终端 |
| 代码编辑 | 基于 Monaco Editor，提供基础代码编辑体验 |
| Git | 状态查看、Diff、暂存、Commit、分支切换/创建、Pull/Push |
| Snapshot | 自动捕获文件变化、时间轴、快照 Diff、预览恢复、恢复 |
| AI Agent | 对话、上下文选择、任务执行、工具调用、任务前后快照、变更审查 |
| 本地数据 | SQLite 元数据 + 本地内容存储；无需账号即可使用核心功能 |

### 2.4 产品边界：暂时不做

MVP 不做以下事情，避免演变成重造 VS Code 或完整 DevOps 平台：

- 不开发完整插件市场、扩展 API 和 VS Code 扩展兼容层。
- 不自研语言服务器、调试器、编译器、运行时或完整 IDE 智能补全体系；优先复用 LSP/现有工具。
- 不自研 Git 协议、对象数据库或远程托管服务；不替代 GitHub/GitLab。
- 不做团队实时协同编辑、云端工作区、代码托管、CI/CD 平台。
- 不在 MVP 支持多 Agent 并行自治、复杂 Agent 编排、长期记忆平台。
- 不默认上传代码、快照或 Agent 上下文到云端。
- 不承诺兼容所有 Git 扩展能力；Git LFS、复杂 submodule、签名提交、特殊凭据链等列为兼容性增强项。

**关键取舍：** MVP 的编辑器是“够用的工作台编辑器”，不是 VS Code 的全面替代；产品差异化来自 Git + Snapshot + Agent 的统一闭环。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 使用 AI Coding Agent 的个人开发者。
- 需要快速迭代、频繁试错的独立开发者 / 一人团队。
- 希望在本地掌握代码和历史数据的小型技术团队。

### 3.2 核心场景

**场景 A：日常开发**
1. 打开本地项目。
2. 在 Monaco 中编辑代码。
3. 工作台自动捕获稳定的文件变化。
4. 在 Git 面板查看差异、暂存并 Commit。

**场景 B：让 Agent 实现功能**
1. 用户描述任务并选择上下文文件。
2. 系统创建 Agent 任务开始快照。
3. Agent 在项目工作区中读取和修改文件、执行允许的命令。
4. 任务结束后自动创建任务结束快照。
5. 用户查看变更文件、Diff、命令记录和任务摘要。
6. 用户选择保留修改、继续迭代，或恢复到任务前状态。

**场景 C：误操作恢复**
1. 用户从统一时间线找到目标快照。
2. 查看该快照与当前工作区的差异。
3. 预览将新增、覆盖、删除的文件。
4. 系统先创建恢复前保护快照，再执行恢复。
5. 恢复结果可再次撤销。

## 4. 产品目标与成功指标

### 4.1 MVP 目标

1. 能打开和管理本地项目，并提供稳定的文件树与 Monaco 编辑体验。
2. 能完成常用本地 Git 工作流。
3. 能自动捕获文件变化，生成独立、可恢复的快照。
4. 能在同一时间线上关联 Git Commit、自动快照和 Agent 任务节点。
5. 内置 Agent 能在用户授权下执行任务，并自动生成前后快照。
6. 恢复操作有预览、保护快照和结果校验。

### 4.2 MVP 不追求

- 替代 VS Code / Cursor 的全部能力。
- 替代 GitHub / GitLab 的远程协作能力。
- 自研基础模型或训练代码模型。
- 账号、团队空间、云同步和插件生态的完整商业化能力。

### 4.3 核心指标

| 指标 | 定义 |
|---|---|
| 快照捕获成功率 | 满足触发条件的变更中成功保存的比例 |
| 恢复一致率 | 恢复后工作区内容与目标快照清单的一致程度 |
| Git 操作成功率 | MVP 覆盖的 Git 操作成功完成比例 |
| Agent 任务闭环率 | Agent 任务能够完成执行、Diff 审查和前后快照关联的比例 |
| 变更审查使用率 | Agent 任务完成后打开 Diff/变更清单的比例 |
| 空闲资源占用 | 无任务时后台 CPU、内存占用 |
| 存储效率 | 内容去重后实际占用与理论重复存储量的比例 |

界面优先保证编辑空间；Git、Snapshot、Agent 是围绕工作区的侧边能力，不应抢占主编辑区域。

## 6. 功能需求与优先级

优先级定义：P0 = MVP 必须；P1 = MVP 后增强；P2 = 长期规划。

### 6.1 Workspace 与 Editor

| ID | 功能 | 优先级 | 验收标准 |
|---|---|---:|---|
| W-001 | 打开本地文件夹 | P0 | 可打开已有项目目录并记住最近项目 |
| W-002 | 文件树 | P0 | 展示目录、文件；支持展开、选择、创建、重命名、删除 |
| W-003 | Monaco 编辑器 | P0 | 支持常见文本文件编辑、标签页、保存 |
| W-004 | 编辑器基础体验 | P0 | 行号、语法高亮、查找、缩进、撤销/重做 |
| W-005 | 集成终端 | P0 | 在项目根目录启动系统 Shell，可执行常见开发命令 |
| W-006 | 全局搜索 | P1 | 支持项目内文件名和文本搜索 |
| W-007 | LSP 语言能力 | P1 | 通过可配置语言服务器增强诊断、跳转和补全 |
| W-008 | 调试器 | P2 | 通过 DAP 或外部调试器接入 |

MVP 的 Monaco 能力以编辑、保存、查找和 Diff 为核心，不承诺完整 IDE 级别的智能补全、重构和调试能力。

### 6.2 Git 集成

| ID | 功能 | 优先级 | 验收标准 |
|---|---|---:|---|
| G-001 | 仓库识别 | P0 | 打开项目后识别 Git 仓库与当前分支 |
| G-002 | 文件状态 | P0 | 展示新增、修改、删除、未跟踪、冲突等状态 |
| G-003 | Diff 查看 | P0 | 支持工作区与 HEAD/暂存区差异查看 |
| G-004 | Stage / Unstage | P0 | 支持单文件及选中变更暂存/取消暂存 |
| G-005 | Commit | P0 | 输入提交信息并创建本地 Commit |
| G-006 | 分支查看与切换 | P0 | 展示本地分支并切换；切换前检查未提交变更 |
| G-007 | 创建分支 | P0 | 基于当前 HEAD 创建新分支 |
| G-008 | Pull / Push | P1 | 支持常规远程仓库同步，并提供错误反馈 |
| G-009 | Remote 管理 | P1 | 查看、添加、修改远程地址 |
| G-010 | Merge / Rebase | P1 | 提供基础操作入口；复杂冲突优先引导到文件级解决 |
| G-011 | Stash / Cherry-pick / Tag | P2 | 后续按用户需求增加 |

**实现原则：** 优先调用系统 Git CLI，保持与用户机器上 Git 配置、SSH Agent、Credential Helper、签名配置和 Git hooks 的兼容性。可以用 Rust 封装命令执行与解析；`git2/libgit2` 可用于特定只读或高频操作，但不把它作为所有 Git 能力的唯一实现。不得直接修改 `.git` 内部文件来模拟 Git 操作。

MVP 的 Git 范围先覆盖本地仓库核心闭环；远程 Pull/Push 可作为 MVP 后半段或 P1，取决于凭据与错误处理的实现质量。

### 6.3 Snapshot 自动快照

| ID | 功能 | 优先级 | 验收标准 |
|---|---|---:|---|
| S-001 | 文件变化监听 | P0 | 捕获新增、修改、删除、重命名 |
| S-002 | 稳定性判定与防抖 | P0 | 文件写入稳定后再读取，避免保存半成品 |
| S-003 | 内容哈希与去重 | P0 | 相同内容只存一份 Blob |
| S-004 | 快照清单 | P0 | 每个快照独立记录路径、内容哈希、文件元信息 |
| S-005 | 自动快照 | P0 | 按防抖/时间窗口/变更规模策略自动生成 |
| S-006 | 手动快照 | P0 | 用户可为当前状态创建命名快照 |
| S-007 | 时间线 | P0 | 展示自动快照、手动快照、Git Commit、Agent 节点 |
| S-008 | 快照 Diff | P0 | 可查看两个快照或快照与当前工作区的差异 |
| S-009 | 恢复预览 | P0 | 展示将新增、覆盖、删除的文件 |
| S-010 | 恢复与保护快照 | P0 | 恢复前创建保护快照，恢复后校验结果 |
| S-011 | 存储管理 | P1 | 展示占用、去重收益和保留策略 |
| S-012 | 快照保留策略 | P1 | 支持按时间/数量清理，并保护手动标记快照 |

快照数据必须独立于 Git 对象数据库；每个快照可独立重建，不依赖脆弱的增量回放链。`.git`、依赖目录、构建产物和用户配置的敏感目录默认排除；`.env` 等敏感文件应明确提示并允许用户配置排除规则。

### 6.4 Agent 集成

| ID | 功能 | 优先级 | 验收标准 |
|---|---|---:|---|
| A-001 | Agent 对话面板 | P0 | 可在工作台内输入任务并查看消息流 |
| A-002 | 模型配置 | P0 | 用户可配置模型供应商、API Key、模型名称与参数 |
| A-003 | 项目上下文 | P0 | Agent 可读取项目文件；用户可选择/排除上下文 |
| A-004 | 文件工具 | P0 | Agent 可读取、创建、修改文件 |
| A-005 | 命令执行工具 | P0 | Agent 可请求执行终端命令；命令权限由用户控制 |
| A-006 | 任务前快照 | P0 | 每个任务开始前自动创建 Snapshot |
| A-007 | 任务后快照 | P0 | 任务完成、失败或中止后记录最终状态 |
| A-008 | 变更审查 | P0 | 展示本次任务改动文件、Diff 和任务摘要 |
| A-009 | 恢复任务前状态 | P0 | 可从任务节点跳转到任务前快照并恢复 |
| A-010 | 工具权限策略 | P0 | 命令执行、文件写入等高风险操作可授权/拒绝 |
| A-011 | Agent 任务历史 | P1 | 保存任务状态、输入、摘要、耗时与关联快照 |
| A-012 | 多 Agent 编排 | P2 | 支持多个 Agent 协作与任务编排 |

**Agent 设计原则：**

1. Agent 不直接绕过工作台文件与快照服务写入数据；所有文件写入必须可被 Snapshot 监听捕获。
2. Agent 命令执行必须有权限边界。MVP 默认对危险命令、外部网络访问、删除操作进行确认。
3. 每次任务有明确的开始、运行、完成、失败、中止状态。
4. 任务前后快照是系统级保护，不依赖模型是否主动调用工具。
5. Agent 结果不能自动 Commit；是否提交由用户决定。
6. MVP 先实现单 Agent、单任务串行执行，不做并行多 Agent。

## 7. 核心交互流程

### 7.1 首次打开项目

1. 用户选择本地目录。
2. 工作台识别是否存在 Git 仓库。
3. 用户确认 Snapshot 忽略规则与存储位置。
4. 系统扫描文件并建立初始快照基线。
5. 进入 Workspace。

### 7.2 Agent 任务闭环

1. 用户在 Agent 面板输入需求。
2. 系统展示任务范围与权限提示。
3. 创建 `agent_task_started` 快照。
4. Agent 读取上下文、编辑文件、执行授权命令。
5. 系统持续捕获变更；任务结束时创建 `agent_task_finished` 快照。
6. 展示任务摘要、文件变更和 Diff。
7. 用户选择继续修改、接受变更，或恢复任务前快照。
8. 如用户认可，可在 Git 面板 Stage 并 Commit。

### 7.3 Git Commit 与 Snapshot 联动

- 每次 Git Commit 在统一时间线生成一个 Git 节点。
- 节点保存 Commit SHA、分支、提交信息和时间。
- Snapshot 可记录最近一次已知 Git HEAD，便于比较“提交版本”和“工作区状态”。
- Git 操作失败不得伪造时间线节点。
- 从 Snapshot 恢复只改变工作区文件，不隐式执行 `git reset`、`checkout` 或修改分支历史。

### 7.4 恢复流程

1. 用户选择目标快照。
2. 系统计算当前工作区与目标快照的文件差异。
3. 展示覆盖、创建、删除文件列表。
4. 用户确认后创建恢复前保护快照。
5. 在临时目录准备目标内容，再安全写入工作区。
6. 校验恢复后的文件清单与内容哈希。
7. 记录恢复事件；失败时保留保护快照并给出可恢复提示。

## 8. 技术架构

### 8.1 技术选型

| 层级 | 技术建议 | 职责 |
|---|---|---|
| Desktop Shell | Tauri 2 | 桌面窗口、系统集成、权限边界、打包 |
| Frontend | React + TypeScript | 工作台 UI、状态管理、交互 |
| Editor | Monaco Editor | 代码编辑与 Diff Editor |
| Core | Rust | 文件监听、Snapshot、存储、Git/Agent 任务编排 |
| Git | System Git CLI + Rust wrapper | Git 命令执行、状态解析、凭据兼容 |
| File Watch | notify + 周期性 reconcile | 监听文件变化并周期校验目录 |
| Hash | BLAKE3 | 内容寻址与快速哈希 |
| Metadata | SQLite | 项目、快照、文件清单、任务、关联关系 |
| Blob Store | 本地文件系统 | 保存内容对象，按哈希寻址 |
| Agent Runtime | 独立 Agent Service / Tool Runtime | 模型调用、工具循环、权限审批、任务状态 |
| Terminal | 系统 Shell PTY | 项目内命令执行 |

### 8.2 架构分层

```text
┌─────────────────────────────────────────────────────────┐
│                  React + TypeScript UI                  │
│ Workspace │ Monaco │ Git │ Timeline │ Agent │ Terminal  │
└───────────────────────────┬─────────────────────────────┘
                            │ Tauri Commands / Events
┌───────────────────────────▼─────────────────────────────┐
│                    Application Layer                    │
│ Project Manager │ Git Service │ Snapshot Service         │
│ Agent Orchestrator │ Restore Manager │ Permission Manager│
└──────────────┬───────────────────────┬──────────────────┘
               │                       │
┌──────────────▼─────────────┐ ┌───────▼──────────────────┐
│       Snapshot Core       │ │       Git Adapter        │
│ notify / reconcile        │ │ system git CLI           │
│ BLAKE3 / Blob Store        │ │ status / diff / commit   │
│ manifest / restore        │ │ branch / remote ops      │
└──────────────┬─────────────┘ └──────────────────────────┘
               │
┌──────────────▼─────────────────────────────────────────┐
│ Local Data Layer                                        │
│ SQLite Metadata + Content-addressed Blob Store          │
│ Project Files + .git (owned and managed by Git)         │
└─────────────────────────────────────────────────────────┘
```

### 8.3 数据存储原则

- Git 仓库仍由标准 Git 管理，`.git` 目录不被 Snapshot 引擎写入。
- SQLite 保存元数据，不直接保存大型文件内容。
- Blob Store 按 BLAKE3 哈希存储内容；快照通过 manifest 引用 Blob。
- 同一内容跨快照复用同一个 Blob。
- Snapshot 的 manifest 是完整文件状态清单，保证任意快照可独立恢复。
- 数据目录与项目目录分离，避免项目删除或 Git 清理误删快照。
- 默认不上传源码、快照和 Agent 上下文；模型 API 请求会发送用户授权的上下文，需在 UI 明示。

### 8.4 核心数据模型（逻辑）

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Project | id, root_path, name, created_at | 本地项目 |
| Snapshot | id, project_id, kind, created_at, reason, git_head | 一次完整状态记录 |
| SnapshotFile | snapshot_id, relative_path, blob_hash, size, mode | 快照文件清单 |
| Blob | hash, size, storage_path, created_at | 内容对象 |
| GitReference | project_id, commit_sha, branch, snapshot_id | Git 节点与快照关联 |
| AgentTask | id, project_id, status, prompt, started_at, finished_at | Agent 任务 |
| AgentTaskSnapshot | task_id, before_snapshot_id, after_snapshot_id | 任务前后快照 |
| TimelineEvent | id, project_id, type, occurred_at, ref_id | 统一时间线事件 |

### 8.5 关键可靠性要求

- 文件监听事件可能合并、丢失或乱序，必须配合周期性目录扫描校验。
- 文件读取前做稳定性判断；处理临时文件、原子替换和大文件。
- Snapshot 写入采用临时文件 + 原子重命名；元数据事务与 Blob 落盘顺序需可恢复。
- 恢复前创建保护快照，恢复过程支持中断后的状态识别。
- 忽略规则需可解释、可预览；避免误排除源码或意外捕获密钥。
- 大文件、二进制文件、符号链接、权限位和重命名需有明确处理策略。
- Agent 工具执行要记录调用、参数摘要、结果和权限决策；密钥不得写入日志。

## 9. MVP 范围与里程碑

### 9.1 MVP 定义

MVP 只做一个可稳定使用的本地开发闭环：

**打开项目 → 编辑代码 → 查看 Git Diff → 创建 Commit → 自动 Snapshot → Agent 修改 → 审查 Diff → 一键恢复。**

### 9.2 MVP 必须交付

**P0 — 工作台基础**
- Tauri 2 + React + TypeScript 桌面应用。
- 打开本地项目、文件树、Monaco 编辑器、标签页、保存。
- 集成终端基础能力。

**P0 — Git 本地闭环**
- 仓库识别、状态查看、Diff、Stage/Unstage、Commit。
- 本地分支列表、创建和切换。
- 远程 Push/Pull 可放入 MVP 后段；若实现不稳定则明确延期，不阻塞本地闭环。

**P0 — Snapshot 闭环**
- 文件监听、忽略规则、防抖、内容哈希、Blob 去重。
- 自动/手动快照、时间线、Diff、恢复预览、恢复与校验。
- 恢复前保护快照。

**P0 — 单 Agent 闭环**
- 配置一个模型供应商/API Key。
- Agent 对话、文件读取/编辑、受控命令执行。
- 任务开始/结束快照、变更清单、Diff、恢复任务前状态。
- 危险操作确认；用户始终拥有最终 Commit 决策权。

### 9.3 明确不进入 MVP

- 插件市场、扩展 API、VS Code 插件兼容。
- 云端账号、跨设备同步、团队协作。
- 多 Agent 并行、复杂工作流编排。
- 完整 LSP/调试器/高级重构。
- Git LFS、复杂 submodule、完整 Git 图形化历史重写工具。
- 远程 Agent 沙箱与云端代码执行。

### 9.4 推荐开发顺序

| 阶段 | 交付 | 阶段验收 |
|---|---|---|
| M0：桌面骨架 | Tauri、React、项目打开、文件树、Monaco | 能打开并编辑真实项目 |
| M1：Git 基础 | 状态、Diff、Stage、Commit、分支 | 能完成日常本地 Git 工作流 |
| M2：Snapshot Core | 监听、Blob、manifest、时间线、恢复 | 任意快照可独立恢复且校验通过 |
| M3：Agent 闭环 | Agent Runtime、工具权限、前后快照、Diff | Agent 修改可审查、可恢复 |
| M4：稳定性与体验 | 性能、异常恢复、打包、文档 | 可交付给真实开发者试用 |

建议先把 M0–M2 做扎实，再接 Agent。Agent 是重要差异化，但不能建立在不可靠的快照底座上。

## 10. MVP 验收清单

- [ ] 能打开一个包含数千个文件的常见前端项目，并正确排除依赖目录。
- [ ] 编辑器能打开、修改、保存常见源码文件。
- [ ] Git 状态与系统 Git CLI 结果一致。
- [ ] 能查看工作区 Diff、暂存变更并 Commit。
- [ ] 文件变化后在设定窗口内生成快照；重复内容不重复保存。
- [ ] 关闭并重启应用后，项目和快照历史仍可读取。
- [ ] 能查看任意两个快照间的文件变化。
- [ ] 恢复前能预览影响，并自动创建保护快照。
- [ ] 恢复后抽样及全量哈希校验与目标 manifest 一致。
- [ ] Agent 任务前后均有快照，即使任务失败或中止也能定位状态。
- [ ] Agent 的文件修改和命令执行均受权限策略约束。
- [ ] Agent 完成后能展示改动文件与 Diff，且不会自动 Commit。
- [ ] 网络断开时，编辑、Git 本地操作和 Snapshot 仍可工作；调用云模型时明确提示网络依赖。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 产品范围膨胀，变成重造 VS Code | 开发周期失控 | 坚持 Monaco + 工作台，不自研语言工具链 |
| Git CLI 输出与平台差异 | 状态解析不稳定 | 结构化输出优先，封装适配层，覆盖 macOS/Windows/Linux |
| Git 凭据与远程操作复杂 | Push/Pull 失败 | 优先复用系统 Git、SSH Agent、Credential Helper；远程能力后置 |
| 文件监听漏事件 | 快照缺失 | 监听 + 周期扫描 reconcile |
| 快照占用空间过大 | 用户磁盘压力 | 内容寻址去重、忽略规则、保留策略 |
| 恢复覆盖用户新修改 | 数据丢失 | 预览、保护快照、原子写入、校验 |
| Agent 执行危险命令 | 项目或系统受损 | 权限审批、命令风险分级、可配置工作区边界 |
| API Key 或源码泄漏 | 安全风险 | 本地密钥存储、上下文透明提示、日志脱敏、默认不上传快照 |

## 12. 产品原则总结

1. **工作台而非 IDE 全家桶：** 只实现能支撑核心闭环的编辑与项目能力。
2. **Git 是正式版本控制：** 不替代 Git，不篡改 `.git`，优先复用系统 Git。
3. **Snapshot 是自动安全网：** 独立于 Git、无需 Commit、任意快照可恢复。
4. **Agent 是受控执行者：** 任务前后有快照，修改可审查，权限由用户掌控。
5. **Local-first：** 本地能力优先，云端模型是可选依赖，不是数据底座。
6. **先可靠再丰富：** 先交付编辑、Git、Snapshot、单 Agent 的完整闭环，再扩展 LSP、远程 Git、插件和团队能力。

---

**产品核心体验：** 开发者不需要在编辑器、Git 客户端、快照工具和 Agent 之间来回切换；每一次人工或 AI 修改都能被看见、被审查，并且在出错时有路可退。
